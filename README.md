# Meeting Rooms API

REST API бронирования переговорных комнат на Node.js (Express) + PostgreSQL. Бронь нельзя создать или перенести на время, которое уже занято в той же комнате.

## Что внутри

- Node.js (Express)
- PostgreSQL (драйвер `pg`, без ORM)
- `db/init.sql` с описанием таблицы `bookings`: схему здесь создаёт не приложение, а этот скрипт

## Структура проекта
```text
meeting-rooms-api/
├── db/
│   └── init.sql
├── server.js
├── package.json
├── package-lock.json
└── .env.example
```

## Как приложение подключается к базе

`pg` сам читает стандартные переменные окружения PostgreSQL: `PGHOST`, `PGPORT`, `PGUSER`, `PGPASSWORD`, `PGDATABASE`. Больше приложение ничего не требует. Порт слушает из `PORT` (по умолчанию `8085`).

Если база при старте недоступна, приложение пишет ошибку и завершается с кодом `1`.

## API методы

В примерах порт `8085`. Если на хосте ты опубликуешь другой порт, подставь свой.

```bash
# приложение живо
curl http://127.0.0.1:8085/health

# приложение видит базу
curl http://127.0.0.1:8085/health/db

# создать бронь (время в формате ISO 8601)
curl -X POST http://127.0.0.1:8085/bookings \
  -H 'Content-Type: application/json' \
  -d '{"room":"Альфа","booked_by":"Олег","start_at":"2026-10-06T10:00:00Z","end_at":"2026-10-06T11:00:00Z"}'

# пересекающаяся бронь той же комнаты даёт 409
curl -X POST http://127.0.0.1:8085/bookings \
  -H 'Content-Type: application/json' \
  -d '{"room":"Альфа","booked_by":"Ірина","start_at":"2026-10-06T10:30:00Z","end_at":"2026-10-06T11:30:00Z"}'

# список (с фильтром по комнате)
curl http://127.0.0.1:8085/bookings
curl "http://127.0.0.1:8085/bookings?room=Альфа"

# по ID
curl http://127.0.0.1:8085/bookings/1

# изменить (достаточно передать изменённые поля)
curl -X PATCH http://127.0.0.1:8085/bookings/1 \
  -H 'Content-Type: application/json' \
  -d '{"booked_by":"Олег Т."}'

# удалить
curl -X DELETE http://127.0.0.1:8085/bookings/1
```

## Задача: запустить через Docker Compose (Node.js + PostgreSQL)

В репозитории нет ни `Dockerfile`, ни `docker-compose.yml`, ни `.dockerignore`, ни `.env`. Всё это нужно написать самостоятельно.

### Часть 1. Основная
1. **Dockerfile** для приложения:
   - базовый образ Node с зафиксированной LTS-версией (не `latest`);
   - зависимости ставятся строго по `package-lock.json` и без dev-пакетов, причём так, чтобы при правке `server.js` слой с зависимостями не пересобирался;
   - запуск напрямую через `node server.js`, а не через `npm start`. Подумай, чем отличаются эти два варианта с точки зрения процессов в контейнере.
2. **`.dockerignore`**: `node_modules`, `.git`, `.env`. Подумай, что произойдёт, если `node_modules` с хоста попадёт в образ.
3. **`.env`** содержит только `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` (см. `.env.example`). Приложению нужны переменные `PG*`, и значения нельзя дублировать руками. Compose умеет подставлять значения из `.env` в сам `docker-compose.yml` (запись вида `${VAR}`). Используй это, чтобы передать в `backend` нужные `PG*` из тех же значений. Хост базы внутри compose-сети не `localhost`.
4. **docker-compose.yml** с сервисами `backend` и `db`:
   - `db`: образ `postgres` с зафиксированной версией, named volume для данных (путь зависит от мажорной версии образа), `healthcheck`, `restart`;
   - схема создаётся скриптом `db/init.sql`: подключи его к контейнеру `db` так, чтобы официальный образ выполнил его при первом старте;
   - `backend`: сборка из твоего Dockerfile, старт только после того, как `db` реально готова, `restart`, опубликованный порт;
   - у `backend` тоже должен быть `healthcheck`. В образе Node нет `curl`, подумай, чем проверить `/health` изнутри контейнера (в Node 18+ есть встроенный `fetch`).
5. Порт базы наружу **не публикуется**. Проверь через `ss -tlnp`, что на хосте нет слушателя на `5432`.
6. Подними всё одной командой, оба сервиса должны быть в статусе `healthy` (`docker compose ps`).
7. Проверь `/health`, `/health/db` и все пять CRUD-эндпоинтов. Отдельно проверь:
   - пересекающаяся бронь той же комнаты отвечает `409`, а вплотную идущая (конец первой равен началу второй) создаётся;
   - `GET /bookings/abc` отвечает `400`, а не `500`.
8. Зайди в `psql` внутри контейнера `db` и посмотри структуру таблицы (`\d bookings`): должны быть индекс и проверка `end_at > start_at`. Логин и пароль руками не копируй, они уже есть в окружении контейнера.
9. Тест на сохранность: `docker compose down` и `up -d`, записи на месте. Затем `docker compose down -v` и `up -d`: записей нет, а таблица при этом есть. Почему таблица появилась заново?

### Часть 2. Эксперименты
**A. `init.sql` выполняется один раз.** Добавь в `init.sql` новую колонку (например `attendees INT`), сделай `docker compose down` и `up -d`. Появилась ли колонка? Что нужно сделать, чтобы скрипт отработал заново, и чем это плохо для настоящей системы с живыми данными? Найди, как называется подход, который решает эту проблему (ключевое слово: миграции).

**B. Остановка за секунды.** Замерь `time docker compose stop backend`. Если выходит около 10 секунд, выясни причину: подсказка в том, каким по счёту процессом внутри контейнера запускается Node и как себя ведёт процесс с PID 1 при получении `SIGTERM`. Добиться быстрой остановки можно двумя способами: ключом сервиса в Compose, который добавляет в контейнер минимальный init-процесс, либо обработкой сигнала в самом `server.js` (код править разрешено). Выбери один, замерь снова, затем подумай, какой подход лучше и почему.

**C. Что даёт условие готовности.** Временно убери из `depends_on` условие готовности базы, сделай `docker compose down -v` и `up -d`. Смотри `docker compose ps` и `docker compose logs backend`: что происходит с `backend` в первые секунды и почему он в итоге всё равно поднимается? Верни условие на место.

**D. Размер образа.** Сравни `node:<версия>`, `node:<версия>-slim` и `node:<версия>-alpine` по размеру (`docker images`). Какой выберешь для продакшена и почему?

Если контейнер падает с кодом `139` и в `dmesg` есть `fork rejected by pids controller`, это тот же лимит процессов, что был в прошлых задачах. Для Compose у сервиса есть соответствующий ключ.
